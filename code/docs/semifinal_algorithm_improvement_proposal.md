# 复赛算法改进建议：先分解收益，再定向改模型

状态：建议稿，2026-09-24。本文只定义实验及验收条件，不代表已经生成或提交新预测。

## 1. 当前事实与问题

- 复赛数据为 1,295 个场景、5,690 条查询，提供 RGB、红外和深度图；本地只有无标注测试集，官方指标为 ACC@0.5，每天最多提交两次。
- [v0.0 零样本管线](../../results/v0.0_zeroshot-baseline_wang_20260922/README.md)官方分为 **0.5996**；v3.0 采用 LoRA 与大量 COCO 合成数据，用户反馈官方分约 **0.61**，精确成绩尚未写入[结果总账](../../results/INDEX.md)。精确分数应先回填，不能把“约 0.61”当作后续实验的固定基准。
- v3.0 的序数外部验证结果未随训练数据量增加而提高，见[v3.0 记录](../../results/v3.0_coco-synth-ordinal_wang_20260924/README.md)。继续增加同类合成样本暂缺收益证据。
- 直接比较已归档的 v0.0 和 v3.0 预测，42.5% 的查询两框 IoU < 0.5；按 `first/second/.../leftmost/rightmost` 等简单正则筛出的 1,247 条序数查询中，这一比例为 63.4%。这是**模型分歧率，不是错误率**，尚不能断定哪一版更好。
- 初赛用 RefCOCO 等外部集做过全局重排、联合赋值和边界精修；[既有记录](best_baseline_and_next_work.md)显示全局重排曾明显退步，联合赋值及边界精修没有达到验收门槛。复赛不能直接沿用初赛的分数阈值或重复这些实验。

因此，第一个待回答的问题是：v3.0 的有限线上增益究竟来自序数题，还是来自其他查询？第二个问题才是错误发生在候选框生成、候选框选择，还是边界定位。

## 2. 第一轮：两次官方提交做分组对照

以同一份官方查询 JSON 为模板，以 v0.0 的 bbox 为控制，按**互斥**规则划分两组：命中预先冻结的序数关键词规则为 `ordinal`，其余全部为 `non_ordinal`。同一查询只能进入一组；规则和 Query ID 清单必须在看提交分数前保存。

| 方案 | `ordinal` 组 | `non_ordinal` 组 | 要回答的问题 |
| --- | --- | --- | --- |
| O：序数替换 | v3.0 bbox | v0.0 bbox | v3.0 是否改善序数题？ |
| N：非序数替换 | v0.0 bbox | v3.0 bbox | v3.0 是否改善其他题？ |

两份预测都必须保留原始 Query ID 顺序和非 bbox 字段；只允许修改 bbox。ZIP 内文件名固定为 `prediction.json`。生成后使用[提交校验脚本](../scripts/validate_submission.py)分别检查 JSON 与 ZIP，再占用当天两次官方提交机会。保存每份提交的代码提交号、源预测哈希、分组清单、改动数量、ZIP 哈希及官方分数。

若官方分数确实是对全部 5,690 条查询取平均，且四份提交使用相同测试集与评分规则，则应有 `score(O) + score(N) ≈ score(v0.0) + score(v3.0)`；允许显示精度造成的舍入差。这个关系可用于检查记录或提交是否混淆。只根据实测结果选择保留哪一组；模型分歧大本身不是替换理由。

## 3. 第二轮：在外部标注集上定位瓶颈

复赛测试集没有真值，不对其人工补框或用其训练。使用现有的 `code/data/validation/refcoco_val.json` 与冻结的 dev/holdout 划分，在[候选框评估工具](../scripts/evaluate_candidates.py)中按序数、空间关系、远近、颜色、小目标分组，至少报告：

1. Top-1 ACC@0.5；
2. Oracle@5/10/20，即前 K 个候选中是否存在 IoU ≥ 0.5 的框；
3. 候选覆盖率、无效框率及框面积分布；
4. 在 Oracle 覆盖的样本上，现有选择器选中正确目标的比例。

外部集用于**诊断故障位置**，不直接折算复赛分数。过去根据初赛表现推算的复赛 v0.0 分数约为 0.29～0.33，而官方实测为 0.5996，说明旧代理分数的跨赛段校准不可靠。

| 观察 | 下一步改动 | 暂缓事项 |
| --- | --- | --- |
| Oracle@20 仍低 | 扩充候选来源；针对小目标测试高分辨率切图、多 Prompt 与直接定位模型 | 继续调候选重排阈值 |
| Oracle@20 高、Top-1 低 | 改同类目标的实例区分、参照物关系、序数家族一致性；只在有歧义的样本上启用二次判别 | 全局替换全部预测框 |
| 已选中正确实例，但框常落在 IoU 0.5 附近 | 单独研究边界精修，要求 dev/holdout 都有净收益 | 把边界精修当作首要方向 |

每个候选改动先固定外部 dev 参数，在未参与调参的 holdout 上复核。既有全局重排和边界精修失败记录应作为负面对照；如果不能解释并克服其失败原因，就停止相同路线。

## 4. 值得试验的算法改动

**优先级 A：独立的完整 Query 定位候选。** 现有“Qwen 解析名词 → Grounding DINO 找框 → Qwen 选框”会受到候选召回限制。可用一个直接接收 RGB 与完整指代表达、直接输出框的模型，先在外部 holdout 和少量复赛无标注样本上运行，比较合法率、推理成本、与现有候选的分歧及外部集 Oracle 增量。一个可研究的开源候选是 [LocateAnything-3B 官方项目](https://research.nvidia.com/labs/lpr/locate-anything/)及[模型卡](https://huggingface.co/nvidia/LocateAnything-3B/blob/main/README.md)；其公开权重面向研究且许可证限制非商业用途，采用前须确认赛事许可。此处是试验建议，**没有证据表明它一定能提高本赛分数**。

**优先级 B：序数题的实例筛选。** 若第一轮证实序数题是主要收益或主要损失来源，再研究同一场景内“第一、第二、第三”等查询的候选集合、对象属性与顺序一致性。先在有真值的外部集证明净收益，再只对高置信度且原方案存在明确冲突的复赛查询替换框。不要直接复用初赛已被拒绝的 V31 联合赋值规则。

**优先级 C：有条件的 RGB/深度/红外融合。** 对比多模态版本和仅 RGB 版本在外部标注集上的逐类收益；深度仅用于远近/前后等相应查询，红外仅用于热相关查询。若某模态在独立 holdout 上没有净收益，就不扩大其路由范围。

暂不继续堆同类 COCO 模板合成数据，也不把两个全量预测简单平均。若后续训练，应优先用允许使用的外部标注数据构造“同类多实例、关系、遮挡、小目标”难例，并冻结独立 holdout；不得用复赛测试图像生成训练标签。

## 5. 验收与交付

1. **第一步**：补齐 v3.0 精确官方分数；冻结 v0.0/v3.0 预测、序数分组规则和所有哈希。
2. **第二步**：产出 O、N 两份可验证的预测和提交包，分别记录官方分数。只有分组实测收益明确，才进入针对性改模。
3. **第三步**：产出外部集的 Top-1/Oracle@K 分类型报告，明确下一项工作属于候选、选择还是边界问题。
4. **第四步**：新模型或新规则须在 dev 与 holdout 上提升，且官方提交只改有依据的目标组；每次提交均保留原始控制预测以便回退。

如果 O/N 都没有超过当前最好成绩，应先修正诊断与验证集适配，再考虑新的全量训练。每天两次提交应对应预先写明的假设，避免根据零散榜单波动反复调阈值。
