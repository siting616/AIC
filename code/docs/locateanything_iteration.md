# 复赛算法迭代：LocateAnything-3B 直接定位分支（v0.1）

状态：2026-09-24 已完成 5690 条全量推理与本地格式校验；尚无本版官方分数。本记录描述已执行实验及下一轮算法选择依据，不把模型分歧当作准确率。

## 1. 为什么增加这条分支

[v0.0 零样本管线](../../results/v0.0_zeroshot-baseline_wang_20260922/README.md)先用 Qwen3-VL 解析查询，再由 Grounding DINO 产生候选，最后由 Qwen 选框。该结构能够利用关系规则和按需路由的深度/红外信息，但目标若未进入候选集合，后续裁决无法补回。v0.1 的假设是：一个直接读取**完整英文指代表达**并生成框的模型，可以提供不同的候选来源，尤其适合候选召回受限的查询。

本版选用 [NVIDIA LocateAnything-3B](https://huggingface.co/nvidia/LocateAnything-3B)，不做微调。它采用 Parallel Box Decoding 输出结构化框，输入为 RGB 与文本。复赛提供的红外和深度图在本版未使用，因此 v0.1 是独立 RGB 零样本基线，不能等同于原多模态管线的完整替代。

## 2. 实际算法与工程流程

```text
原始 queries.json 的 Query ID、英文描述和 visible 路径
  → 按场景复用 RGB 图像读取；最长边缩到 1792（原图较小则保持）
  → 单目标提示词 + LocateAnything-3B BF16 Hybrid 解码
  → 解析 <box><x1><y1><x2><y2></box>，坐标 / 1000
  → 过滤无效框；无框时以 1536、1024 上限自动重试
  → 暂取首个合法框；保留原始回答与框数量
  → 逐条追加 JSONL 断点；构建原始字段不变的结果 JSON 和 ZIP
```

- 提示词模板：`Locate a single instance that matches the following description: {query}.`
- 解码：`generation_mode=hybrid`、`do_sample=False`、`max_new_tokens=128`。输入图像最长边 1792；1920×1080 的标准 SDPA 路径曾在 24 GB 4090 上 OOM，1792×1008 可以稳定运行。官方 `la_flash` 路径在当前环境缺少 `flash_attn.flash_attn_varlen_func`，本轮未启用。
- 坐标：只接受四个有序、有限且位于 `[0,1]` 内的坐标，最终输出为 visible 坐标系。
- 断点：每条记录模型原文、全部解析框、所用尺寸、耗时和错误；恢复时跳过已有合法框。代码是[本次使用的全量脚本](../scripts/locateanything_full_run_v01.py)，与服务器运行版本 SHA-256 相同。

## 3. 分辨率消融与全量运行

同一批按 JSON 顺序均匀抽取的 80 条无标签 Query：

| 最长边 | 运行错误 | 单框 | 多框 | 单条耗时中位数 | 峰值显存 |
|---|---:|---:|---:|---:|---:|
| 1024 | 0 | 72 | 8 | 0.392 秒 | 9.156 GB |
| 1792 | 0 | 78 | 2 | 2.227 秒 | 19.711 GB |

两种分辨率首框的 IoU 中位数为 0.954，但有 12/80 条低于 0.5。分辨率改变了部分小目标、序数与遮挡查询的目标选择；由于没有真值，不能据此认定较高分辨率一定更准。本次全量选 1792，依据是 80 条中更少的多框异常以及显存可承受。

全量共 5690 条，原始运行墙钟时间约 219.1 分钟，单条耗时中位数 2.249 秒，峰值预留显存 20.062 GB。21 条触发自动重试；最终 5395 条单框、295 条多框，后者暂取首框。`004054_002` 原始输出 `<box><741><106><559><192></box>` 的横坐标逆序，三次尺寸上限重试实际都使用 640×360 原图，因此原始运行留下 1 个缺框。归档版随后用用户指定目标外观的定向改写提示词补推，记录了新提示词与原始输出。该操作不属于统一自动算法，见[结果记录](../../results/v0.1_locateanything-3b_ljl_20260924/README.md)。

## 4. 与现有模型的关系

对相同 5690 条无标签查询计算首框 IoU：

| 对照 | 全体 IoU < 0.5 | 序数子集 IoU < 0.5 | 关系子集 IoU < 0.5 |
|---|---:|---:|---:|
| v0.1 vs v0.0 | 39.03% | 58.21%（1218 条） | 35.71%（1193 条） |
| v0.1 vs v3.0 | 35.34% | 50.08%（1218 条） | 29.42%（1193 条） |

子集由[分析脚本](../scripts/analyze_locany_iteration.py)中的关键词规则定义，可重叠。这些数字只说明模型定位不同；官方测试集无标签，不能推断谁更准确，也不能直接平均相距很远的框。v0.0 已有官方分 0.5996；v0.1 未提交，尚不能声称榜单提升。硬件不同，单条耗时也不构成严格的同机吞吐对照。

## 5. 下一轮算法迭代

1. **统一处理无效框。** 对所有无效输出应用相同的自动规则，例如原 Query 的 Slow 解码或预先冻结的通用重提示词，并保存原始回答；不得依赖测试图像的人工目标提示。先在单条失败记录上验证格式，再跑批量回归。
2. **处理多框和重复框。** 295 条多框中的首框未必是目标。加入框去重、合理面积与语义关系约束，并以现有 Qwen/DINO 管线作候选裁决备选；替换门槛应来自有依据的验证或正式榜单对照。
3. **保留模态优势。** LocateAnything 仅处理 RGB。热辐射和远近等描述可让原管线有条件读取红外、深度，同时所有输出仍映射到 visible 坐标。
4. **冻结可比较实验。** 保留 v0.0、v3.0、v0.1 原始预测及版本哈希。若不用外部验证集，每次官方提交前写明唯一假设和改动 Query 集，保存平台分数；不把测试集人工检查当作准确率评测。

## 6. 归档边界

[v0.1 结果目录](../../results/v0.1_locateanything-3b_ljl_20260924/README.md)包含用户要求原样保留的 ZIP。其内部文件为 `submission.json`，而仓库既有平台记录要求 `prediction.json`；本轮只归档，不修改该 ZIP 或提交平台。结果中有一条用户目标裁图指导的定向补推；正式参赛前须按赛题“预测结果由算法自主推理、不得人工干预”的约束替换为统一自动回退。模型权重的 NVIDIA 非商业许可也需按赛事口径确认。
